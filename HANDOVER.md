## Things that bit during this build — read before you hit the same wall

1. **This Next.js (16.3.3) is not the one in your training data.** `AGENTS.md` in the repo root says so explicitly and is regenerated by `next dev` — don't delete it. Concretely different from what you probably remember: middleware is renamed **Proxy** (`src/proxy.ts`, not `middleware.ts`, same behavior); `params`/`searchParams` are `Promise`s everywhere (pages *and* route handlers); route handlers use a generated `RouteContext<'/path'>` type helper (run `npx next typegen` after adding/changing any dynamic route, or `tsc` will fail on a type that doesn't exist yet — I hit this repeatedly and it's always the fix); Server Actions/`<form action={fn}>` is the documented mutation pattern.

2. **Prisma 7 also changed underneath me.** `npm install prisma` pulled `8.0.0-rc.12` (the `latest` dist-tag currently points at a release candidate) — deliberately pinned to `7.10.0` instead, a real stable release. Prisma 7's config moved out of `schema.prisma`: there's a `prisma.config.ts` at repo root holding the datasource URL, and the generator is `provider = "prisma-client"` (not `prisma-client-js`) writing to `src/generated/prisma` (gitignored, regenerated via `npm run db:generate` / `postinstall`). **Driver adapters are now mandatory** — `src/lib/db.ts` constructs `new PrismaClient({ adapter: new PrismaPg({ connectionString }) })`, there's no more implicit connection-string-in-schema. If you see `@prisma/client` import errors, check you're importing from `@/generated/prisma/client`, not the bare `@prisma/client` package (that package is still an installed dependency because the generated client's internals need it at runtime, but you should never import from it directly).

3. **`prisma migrate dev` refuses to run non-interactively**, including for harmless warnings (like adding a unique index to an empty table). The workaround used for every migration after the first one — safe, non-destructive, use it:
   ```bash
   npx prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --script > /tmp/diff.sql
   # hand-create prisma/migrations/{UTC-timestamp}_{name}/migration.sql with that content
   npx prisma migrate deploy   # never prompts
   ```
   Also: **`prisma migrate reset` has a built-in AI-safety guard** — it refuses to run if it detects it was invoked by an AI agent, and requires the exact text of a human's explicit consent message passed via `PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION`. This happened once in this build (reconciling a throwaway test table against a fresh local dev DB with zero real data) — I asked the user first via `AskUserQuestion`, they said yes, I passed their literal answer text. **Do not reuse that pattern casually** — it's a real safety mechanism, treat every future trigger of it as a fresh confirmation required, never assume standing consent.

4. **`server-only` (the npm package, not a Next.js built-in) unconditionally throws when imported outside Next's own bundler** — its package.json only resolves to a no-op under a `"react-server"` export condition that Next's webpack/Turbopack sets; plain Node (a `tsx` script, Vitest) doesn't set it and gets the throwing `index.js`. This bit both the seed script and the test suite:
   - **Seed script** (`scripts/seed-demo.ts`): constructs its own `PrismaClient` instead of importing the guarded `src/lib/db.ts` singleton, and several genuinely-low-risk utility modules (`pdf/resume-pdf.tsx`, `pdf/extract-text.ts`, `storage/*`, `qr/generate.ts`, `qr/token.ts`, `auth/password.ts`) had their `"server-only"` guard **removed** — deliberate, reasoned in `docs/SECURITY.md`'s framing: these don't hold secrets at module scope, and would fail to bundle into a client component anyway (Node-only APIs). The genuinely secret-holding modules (`crypto.ts`, `db.ts`, `session.ts`, `oauth.ts`, `ai/client.ts`, `email/resend.ts`, and everything in `applications/`/`candidate/`/`employer/` that orchestrates them) **kept the guard**.
   - **Tests**: instead of stripping more guards, `vitest.config.ts` aliases `"server-only"` to a no-op **only inside the test runner** — the real guard Next enforces for the browser bundle is untouched. This is the better pattern; if you're tempted to strip another guard for a tooling reason, prefer this alias approach first.
   - **Do not try `--conditions=react-server` as a workaround** — it "fixes" the `server-only` resolution but then breaks `@react-pdf/renderer`'s `hyphenate` dependency's conditional exports under `tsx`'s custom resolver (confirmed, wasted real time on this, not worth re-trying). This is why the seed script writes the demo resume as **plain text**, not a rendered PDF — `@react-pdf/renderer` itself works fine through Next's real bundler (confirmed via a full `next build`), it's specifically broken under `tsx`'s CJS/ESM interop for this one dependency.

5. **A real security bug was caught and fixed during manual testing, not by a linter**: `GET /api/employer/jobs/[id]/applicants` originally did `candidateProfile: { include: { user: true } }`, which serialized `User.passwordHash` into the JSON response for any employer looking at their own applicant list. Found by actually reading a live curl response during end-to-end testing. Fixed to an explicit `select`. Grepped the rest of the codebase for the same `include: { user: true }` pattern afterward — nowhere else does this. **If you add a new route that joins through `CandidateProfile` to `User`, use `select`, not `include`, or you'll reintroduce this.**

6. **Next's ESLint config enforces a React "purity" rule** that flags `Date.now()` (or any impure call) inside a component function body, including Server Components — caught building the apply-flow timing display. Fix pattern used: compute timing *inside a non-component function* (`prepareApplication()` in `src/lib/applications/service.ts` now returns `serverPrepareMs` itself) and pass the number down as a prop, rather than calling `Date.now()` in a page/component body.
